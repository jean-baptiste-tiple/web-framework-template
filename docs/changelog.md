## 2026-09-14 — Le harnais Lighthouse sert en gzip (le score mesuré était celui d'un site non compressé)
- **`scripts/audit-lh.mjs`** : le serveur statique du harnais compresse les types texte (HTML, CSS, JS, JSON, XML, SVG) quand le client l'accepte, avec `Vary: Accept-Encoding`, au-dessus de 1 Ko. Lighthouse simule le réseau à partir des octets réellement transférés : sans compression, la feuille de style d'un site pilote comptait pour 190 Ko au lieu des 28 Ko qu'un hébergeur envoie, soit environ 0,9 s de premier rendu fictif.
- **Effet mesuré** (site pilote, 8 pages) : performance 89 à 94 avant, **98 à 100** après, sans toucher une ligne de rendu. Les autres catégories étaient déjà à 100. Le diagnostic d'avant était incohérent (TBT 0 ms, CLS 0, seuls FCP et LCP en cause) : c'était la signature de l'instrument.
- **Règles écrites** : `.claude/conventions/performance.md § Lighthouse` (le harnais sert ce que le host sert ; vérifier l'instrument avant de corriger un score bas). Journalisé dans `docs/learnings.md`.

## 2026-09-14 — Cible tactile du `<summary>` d'Accordion au plancher de 44px
- **`ui/Accordion.astro`** : le `<summary>` gagne `min-h-11` (2,75rem = 44px, échelle Tailwind, aucune valeur arbitraire). Mesuré à 390 sur un site dérivé, un libellé d'une seule ligne ne faisait que **27px** de haut : la hauteur venait du texte, donc un libellé sur deux lignes (48px) passait le plancher craft-floor et un libellé court le ratait. `items-center` était déjà posé et recentre libellé et chevron dans la hauteur garantie ; les libellés sur deux lignes ne bougent pas, le chevron n'est pas touché, aucune prop ajoutée.
- **Effet hérité** : le correctif porte sur l'atome canonique, donc il remonte sans rien d'autre à `Faq.astro`, `GlobalFaq`, la variante `content.faq-accordion` et tout site dérivé du template.
- **Règle écrite** : `.claude/checklists/code-review.md § Craft` gagne le point « cibles tactiles ≥ 44px mesurées à 390 sur les contrôles d'UNE ligne, hauteur garantie par une classe de l'échelle ». Journalisé dans `docs/learnings.md`.
- **Vérifié** : lint vert ; `astro check` 0 erreur / 0 warning / 2 hints préexistants (`scripts/parity/`) ; build 11 pages. Delta CSS contre un build d'avant le correctif : **1 sélecteur ajouté, 0 retiré** (`.min-h-11{min-height:calc(var(--spacing) * 11)}`). Diff HTML, hash du bundle neutralisé : 5 pages changent (les 5 qui rendent un accordéon), chacune par **le seul jeton `min-h-11`** ajouté à ses `<summary>` (15 au total), zéro suppression ; les 6 autres pages, `llms.txt`, `robots.txt`, `rss.xml`, `sitemap.xml` et `_astro/` (images) sont identiques octet pour octet.
- **Option d'un cran plus simple écartée** : poser le plancher en agrandissant le padding du `<details>` (`p-4` → plus), qui n'aurait coûté aucune classe neuve. Écartée parce que le padding du parent n'entre pas dans la cible cliquable du `<summary>` (cliquer la gouttière n'ouvre pas le volet) : le seuil aurait paru tenu à la mesure de la carte sans l'être sur le contrôle, et la densité de TOUS les accordéons aurait changé, y compris ceux à deux lignes déjà conformes.

## 2026-09-14 — `audit:lh` piloté par le socle (fin des échecs chrome-launcher)
- **`scripts/audit-lh.mjs` (nouveau)** : `pnpm run audit:lh` ne passe plus par `npx --yes @lhci/cli autorun`. Le script sert `dist/` sur un port libre (serveur `node:http`), lance LUI-MÊME Chrome (profil dédié `%TEMP%/audit-lh-*`, `--remote-debugging-port=0` relu dans `DevToolsActivePort`), appelle l'**API** Lighthouse — qui ne fait que se connecter au port CDP — puis ferme son Chrome par `Browser.close` (CDP) et efface son profil avec retry.
- **Pourquoi** : 2 occurrences documentées (docs/learnings.md, 2026-09-14) de `lhci` qui audite la 1re page avec de bons scores puis s'effondre à l'extinction de Chrome — `taskkill` n'atteint pas les processus enfants, puis `EPERM` sur `rmSync` du profil temporaire. La cause est chrome-launcher, utilisé par lhci ET par la CLI Lighthouse (`cli/run.js` relance toujours son propre Chrome quand l'hôte est localhost, `--port` ou pas) : passer par l'API le sort du circuit. Un profil qui résiste à l'effacement est désormais un avertissement, jamais un échec d'audit.
- **`lighthouserc.json` reste la source unique** : le script y lit les URL (`ci.collect.url`), le dossier servi (`staticDistDir`), le dossier de rapports (`ci.upload.outputDir`) et les seuils (`ci.assert.assertions`, clés `categories:*`). Les catégories auditées sont exactement celles qui portent un seuil — ajouter ou retirer une assertion suffit, le script ne redit aucune liste. `numberOfRuns` ≠ 1 est signalé comme ignoré (1 run par URL).
- **Sortie** : une ligne par page pendant le run, puis un tableau page × catégorie, une ligne `ECHEC` par seuil manqué et code de sortie 1 (code 2 pour une panne d'outillage : `dist/` absent, Chrome introuvable, Lighthouse irrésolvable).
- **Zéro dépendance déclarée en plus** : Lighthouse est résolu dans les `node_modules` du projet s'il y est, sinon via `npx --yes --package=lighthouse` une seule fois par run (~5 s, contre ~30 s si on relançait `npx --yes lighthouse` par URL). Chrome = celui du système, `CHROME_PATH` pour en désigner un autre.
- **Retombée documentaire** : `src/content/blog/zero-javascript-par-defaut.md` affirmait que « la commande `pnpm run audit:lh` construit le site puis lance Lighthouse ». C'était vrai de `lhci autorun`, plus du script : il exige un `dist/` existant et sort en code 2 s'il n'en trouve pas. Phrase corrigée (« Après un build, la commande `pnpm run audit:lh` audite le dossier `dist`… Elle ne construit pas le site »), `updatedDate` bumpée au 2026-09-14. La réponse de FAQ du même article (« lance Lighthouse sur le dossier dist ») était déjà exacte, non touchée.
- **Vérifié** : `pnpm run audit:lh` → 4 pages, 100/100/100/100, exit 0 (~45 s) ; zéro `chrome.exe` orphelin et zéro profil `audit-lh-*` résiduel après le run (contrôle sur la ligne de commande des processus + `%TEMP%`). Seuil `categories:performance` porté à 1.01 : cellules marquées `!`, 4 lignes `ECHEC`, exit 1 ; seuil remis à 0.95. Lint vert.
