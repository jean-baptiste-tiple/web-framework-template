# Déploiement

- Build statique -> dist/. Aucun runtime.
- Gate avant tout déploiement : lint + astro check + build + audits (liens morts, images sans dimensions, meta manquantes) — jamais `build` seul. CI : .github/workflows/ci.yml.
- Hébergement : tout host statique (Vercel/Netlify/Cloudflare Pages/GitHub Pages/CDN de stockage). Brancher le repo.
- Mapping branche → environnement déclaré EXPLICITEMENT ici. **Défaut du socle : `main` = TEST, production par l'action « Mise en ligne »** (§ Circuit branches → TEST → production ci-dessous, ADR 0002). Site sans Vercel (stockage statique, autre hébergeur sans aperçus) : un seul environnement, `main` synchronisée avec le site public, le push sur `main` EST la mise en production, l'aperçu local (`pnpm dev`) tient lieu de TEST ; il le déclare ici et surcharge `branches`, `envoyer-sur-test`, `publier` et `statut-mise-en-ligne` par leur `projet.md`.
- Mise en production = validation humaine explicite et informée : récapituler ce qui part en ligne (`git log --first-parent production..origin/main` + `git diff --stat production origin/main`, traduits en changements visibles) et obtenir AVANT le lancement de l'action une validation sans ambiguïté sur ce récap — pas un « vas-y » en passant. Procédure : skill `publier`.
- Préprod (TEST, aperçus) servant le même build que la prod : ses canonical pointent vers la prod (voulu) ; la préprod ne doit PAS être indexée — header `X-Robots-Tag: noindex` posé côté host/CI. Ne PAS copier cette étape dans le workflow de production.
- Si CDN : purger le cache après le sync, sinon l'ancien build reste servi.
- Vérifier un déploiement : l'exécution de l'action « Mise en ligne » EST le déploiement de production (verte = construite et en ligne ; sur un hébergeur alimenté par la CI, le run CI) ; contre-vérifier par `curl -s` sur l'URL, filtré sur le texte attendu. « C'est en ligne ? » se répond en situant le commit visé par rapport à `origin/main` (TEST) et au tag `production` (skill `statut-mise-en-ligne`).
- Redirections : SOURCE UNIQUE = bloc `redirects` d'astro.config.mjs. En `output: static`, cela génère des stubs meta-refresh (200) : doubler de vraies 301 côté host/CDN si le référencement compte. En migrant d'hébergeur, supprimer la config de l'ancien (jamais deux sources de vérité).
- URL de prod : UNE seule fois, `site` dans astro.config — canonical, sitemap.xml, robots.txt, llms.txt, RSS et JSON-LD en dérivent tous.
- Secrets/variables d'env requis par la CI : listés ici, jamais commités. Distinguer ceux inlinés AU BUILD (ex. PUBLIC_FORM_ENDPOINT — à définir dans l'env de build de l'hébergeur, pas seulement en .env local) de ceux d'outillage.
- Réglages host attendus (Lighthouse best-practices + perf) : compression brotli/gzip, cache long + immutable sur `/_astro/*` (assets hashés), HTTP/2 ou 3, redirection unique http→https/apex→www (pas de chaîne). Se vérifie sur l'URL déployée : `curl -sI` (content-encoding, cache-control) — les hosts statiques managés (Vercel/Netlify/CF Pages) le font par défaut, un CDN de stockage NON.
- Contrôles post-déploiement (prod) : 1) 404 réelle : `curl -s -o /dev/null -w "%{http_code}" <domaine>/chemin-inexistant` → 404 (config host, voir seo-geo.md § Agentic). 2) Négociation Markdown : `curl -sI -H "Accept: text/markdown" <domaine>/` → `content-type: text/markdown; charset=utf-8` et `vary: accept` ; même en-tête sur un chemin inexistant → `404` avec un corps Markdown ; sans l'en-tête → HTML inchangé. 3) Lighthouse sur l'URL de prod ≥ seuils de performance.md. 4) `npx is-agentic <domaine> --json` → zéro issue tier essential.

## Circuit branches → TEST → production (défaut du socle, ADR 0002)
Une seule branche durable, `main` ; aucune branche `test` ni `production` (le menu des branches de Claude Code en ligne ne montre que `main`). Règles de session et vocabulaire : CLAUDE.md § Circuit de publication. Adresses du site : CLAUDE.md § Projet (TEST, modèle d'aperçu) et `site` d'astro.config (production).
- Mapping :
  - toute branche de chantier → aperçu Vercel `https://<projet>-git-<branche>-<équipe>.vercel.app`. Nom de branche : le sujet seul (`refonte-tarifs`), sans préfixe de client, de site ni d'ID de tâche (le dépôt dit déjà le client ; l'ID va dans le message de commit : exception assumée à une règle commune de préfixe par ID), minuscules sans accent, chiffres, tirets, 25 caractères au plus, contrôlé par la CI (job « nom de branche » de `.github/workflows/ci.yml`) (au-delà, Vercel abrège l'adresse : elle n'est plus prévisible) ;
  - `main` → TEST, domaine rattaché à `main` dans Vercel (Settings > Domains, « Git branch » = `main`). Déploiement Vercel de type Preview ;
  - production = le commit marqué par le tag `production`, déployé par `.github/workflows/production.yml` (Vercel CLI `deploy --prod`). Dans Vercel, la branche de production est `deploiement-par-action`, qui n'existe pas : aucun envoi git ne déploie la production.
- Invariants git : une modification courte se fait directement sur `main` (copie détachée sur `origin/main`, envoi `HEAD:main`) ; un chantier a sa branche, partie d'`origin/main`, qui rejoint `main` par une fusion `--no-ff` « TEST : <sujet> » ; jamais de fusion de `main` dans une branche de chantier ; 2 branches de chantier en cours au plus par personne. Seule l'action déplace le tag `production` (déclenchée par le skill `publier`, sur un oui) et pose un tag daté `mise-en-ligne-AAAAMMJJ-HHMM` (historique, retour en arrière) ; jamais de tag posé à la main. Fusions dans un worktree temporaire détaché sous `.claude/worktrees/` (ignoré par git), jamais en changeant la branche de la copie de l'éditeur. Garde-fous machine : `deny` de `.claude/settings.json` (push forcé, `reset --hard`, `clean`, suppression de `main`, envoi ou réécriture de tags). Procédures : skills `branches`, `envoyer-sur-test`, `publier`, `annuler-modification`.
- Gates : envoi sur TEST ou sur une branche = contrôle léger (JSON relu, `pnpm run lint` si du code a changé) puis construction complète par Vercel ; fusion d'une branche dans TEST = aperçu construit sur son dernier envoi ; mise en ligne = TEST construit sur le commit envoyé, puis construction de production par l'action. La CI (`ci.yml` : lint + build) tourne en plus sur chaque envoi sur `main` et chaque pull request.
- Publication programmée : un article à `pubDate` future est absent du build de production (`VERCEL_ENV=production`, `getPosts` de `src/lib/blog.ts`, seule porte d'accès aux articles) et visible sur TEST, les aperçus et en local. L'action « Mise en ligne » reconstruit chaque jour à 04:00 UTC la production depuis le tag `production` (6 h à Paris l'été, 5 h l'hiver). Ni Vercel Cron ni fonction serveur (règle absolue 1).
- Bibliothèque des composants `/styleguide/` (ADR 0003) : même porte, absente du build de production (`VERCEL_ENV=production`, `GALLERY_ENABLED` de `src/lib/styleguide.ts`), présente sur TEST, les aperçus et en local. Contrôle : `VERCEL_ENV=production pnpm build` puis `find dist -ipath '*styleguide*'` vide ; `curl -s -o /dev/null -w '%{http_code}' <production>/styleguide/` → 404.
- Réglages du dépôt GitHub (Settings > Secrets and variables > Actions) : secret `VERCEL_TOKEN` (jeton du compte Vercel), variables `VERCEL_ORG_ID` et `VERCEL_PROJECT_ID` (`orgId`, `projectId` de `.vercel/project.json` après `vercel link`). Sans `VERCEL_PROJECT_ID`, la reconstruction planifiée est sautée (dépôt du socle, site pas encore branché) ; une mise en ligne échoue avec un message qui nomme le réglage absent.
- Sessions cloud (claude.ai/code, ou desktop en mode « Cloud ») : copie neuve du dépôt dans une machine Anthropic, rien à installer chez l'éditeur. Par personne : abonnement Claude avec sessions cloud, compte GitHub invité sur le dépôt, application GitHub « Claude » installée sur le dépôt. Environnement cloud en accès réseau « Custom » avec `*.vercel.app` (et les domaines propres de TEST et de la production) en plus de la liste « Trusted » : sans eux, Claude ne peut pas contrôler TEST ni les aperçus (`branches` § 5.3). La passerelle GitHub accepte l'envoi sur toute branche, refuse l'envoi de tags (d'où l'action pour poser `production`) et la suppression d'une branche (`branches` § 7.4) ; elle laisse déclencher l'action par l'API REST (`publier` § 3).
- Accès et indexation : aperçus, TEST et production s'ouvrent avec le lien (protection Vercel « Vercel Authentication » désactivée, sinon les éditeurs sans compte Vercel ne voient rien). TEST et aperçus servent le même build que la production : ils ne doivent PAS être indexés, la production si (contrôle : `curl -sI <adresse TEST>` porte `x-robots-tag: noindex`, `curl -sI <production>` non). Mécanisme : § Vercel.

## Vercel (`vercel.json` du socle)
- Indexation : la première route pose `X-Robots-Tag: noindex, nofollow` sur tout hôte sauf le domaine public (`missing` host). Au bootstrap, remplacer `example.com` par le domaine de `site` d'astro.config (sans `https://`) ; oublié, le site public n'est pas indexé (contrôle : bootstrap, étape 7).
- Commande de build du projet Vercel : `rm -f node_modules/.astro/data-store.json && pnpm astro build`. Le cache de build Vercel restaure `node_modules/.astro` : les images déjà optimisées (`assets/`) sont réutilisées, le cache de contenu (`data-store.json`) est purgé, sinon une page supprimée ou renommée peut survivre. `astro check` n'y tourne pas (gain ~20 s par construction) : il reste dans `/commit-push` et dans la CI, dont le cache est limité à `node_modules/.astro/assets`.
- Le fichier est écrit en forme `routes` UNIQUEMENT (ordre d'évaluation explicite ; les clés de haut niveau `headers`/`redirects`/`rewrites` ne s'y ajoutent pas : un réglage de plus = une route de plus, ex. `X-Robots-Tag: noindex` de préprod = `{ "src": "/(.*)", "headers": { "X-Robots-Tag": "noindex, nofollow" }, "continue": true }` en tête).
- Ce qu'il porte : `Vary: Accept` sur toute réponse ; alias 308 `/about` → `/a-propos` et `/privacy` → `/politique-de-confidentialite` (doublent `redirects` d'astro.config, source unique) ; réécriture `Accept: text/markdown` → jumeau `.md` (routes placées AVANT `handle: filesystem`, parce que Vercel sert le filesystem avant les `rewrites` de haut niveau, donc une page existante ne peut pas être négociée autrement) ; en phase `handle: error`, `404.md` avec statut 404 pour les mêmes agents.
- `has` (condition sur l'en-tête Accept) ne s'exerce pas dans `vercel dev` : la négociation se vérifie sur un déploiement (preview ou prod), jamais en local. Autre hébergeur : écrire l'équivalent (Netlify `_redirects` avec condition de header, Cloudflare Pages `_headers`…) ou accepter que seul le chemin `.md` fonctionne — llms.txt ne promet que celui-ci.
- Un site dérivé qui possède déjà un `vercel.json` de haut niveau le convertit en `routes` au merge du socle (une seule forme par fichier).
